# AI Notes 工程工作流

这份文档定义 `AI Notes` 项目的固定开发流程，用来约束后续每一轮功能、修复、重构和测试建设。

目标不是增加流程负担，而是避免每次都重新讨论“应该先做什么、怎么提交、哪些文档要更新”。

## 核心原则

### 1. 先对齐目标，再动代码

每次开工前必须先明确：

- 这轮要解决什么问题
- 不解决什么问题
- 成功标准是什么
- 有没有高风险边界需要先确认

如果目标不清晰，先出计划，不直接改代码。

### 2. 小步推进，优先可验证

优先做：

- 可分批交付的小改动
- 有清晰验证方式的改动
- 能直接提升稳定性、可维护性或用户体验的改动

避免：

- 一口气跨多个主题的大改动
- 混合功能、重构、样式和无关清理

### 3. 行为变更要有保护

只要涉及以下任一项，必须补验证：

- 用户可见交互
- API 路由
- 数据结构
- 权限逻辑
- 导入 / 导出 / AI 调用链路

验证方式优先级：

1. 自动化测试
2. `lint` / `tsc` / `build`
3. 明确记录的人工冒烟测试

### 4. 文档和代码同步

如果本轮改动影响了以下任一项，必须同步更新文档：

- 产品能力
- 启动方式
- 数据库迁移
- 测试命令
- 模块边界
- 项目结构

最低要求：

- 更新 `README.md`
- 如涉及架构或测试分层，再更新 `docs/architecture/*` 或 `docs/testing/*`

### 5. 复杂逻辑补中文注释

不是所有代码都要加注释，但以下内容应优先补中文说明：

- 为什么这样设计
- 关键状态联动
- 安全边界
- 失败回退逻辑
- 复杂提取 / 评分 / 聚合逻辑

禁止写无信息量注释，例如“给变量赋值”“设置状态”。

### 6. 长对话必须做上下文重锚

当对话已经很长、主题多次切换、或者中途被打断后，禁止直接沿用上一轮总结继续执行。

恢复工作前必须先重新确认：

- 当前真实目标
- 当前明确不做的范围
- 当前 Git 分支
- 当前工作区是否干净
- 当前未提交改动是什么

优先级规则：

1. 先看代码和 Git 状态
2. 再参考聊天记录
3. 不允许只凭上一条总结继续做事

这条规则的目的，是避免“上一轮总结内容被误当成这一轮执行目标”。

## 标准执行流程

### 阶段 1：目标对齐

每轮开始时：

1. 复述目标
2. 明确边界
3. 判断是功能、重构、测试还是修复
4. 给出实现计划

如果上一轮刚做过总结、回顾、收口，或者当前线程曾被中断：

5. 先重锚当前状态
6. 再进入执行

### 阶段 2：开分支

从 `main` 拉新分支，分支名统一使用：

```text
codex/<type>-<topic>
```

常见示例：

- `codex/feat-collection-qa`
- `codex/fix-workspace-layout-default-selection`
- `codex/refactor-article-import`
- `codex/docs-workflow-skill`

### 阶段 3：实现

实现阶段要求：

- 只做当前主题内的改动
- 避免引入无关文件差异
- 优先保持行为兼容
- 如果是重构，优先“只拆结构，不改行为”

### 阶段 4：同步 README 与注释

在实现完成但还没提交前，检查：

- `README.md` 是否需要更新
- 架构文档是否需要更新
- 测试文档是否需要更新
- 新增复杂逻辑是否已补中文注释

### 阶段 5：校验

默认最小校验集：

```bash
npm run lint
node_modules\.bin\tsc.cmd --noEmit
npm run test:run
npm run build
```

如果某项无法运行，必须明确说明原因。

### 阶段 6：提交与推送

提交信息采用 Conventional Commit 风格：

- `feat: ...`
- `fix: ...`
- `refactor: ...`
- `test: ...`
- `docs: ...`

推送后必须提供：

- PR 链接
- PR 标题
- 中英文 PR 描述

### 阶段 7：收口

只有在 PR 已经合并进 `main` 后，才执行收口：

1. 切回 `main`
2. `git pull --rebase origin main`
3. 删除本地分支
4. 删除远端分支
5. 确认远端只保留 `main`

## 特殊规则

### 自动生成文件

如果出现这类自动生成差异：

- `next-env.d.ts`
- `.next/types/*`

默认先判断是否属于噪声。

如果只是构建副产物带来的切换，不要提交。

### 环境文件

绝不提交：

- `.env.local`
- 真实 API Key
- 任何用户私密配置

### 数据库与权限

涉及 Supabase 时：

- 权限边界优先放数据库 / RLS / RPC
- 前端按钮隐藏不是权限控制
- 高风险权限改动必须补测试或 SQL 验证

### 测试策略

当前测试建设顺序已经明确：

1. 单元测试
2. API 集成测试
3. 组件集成测试
4. E2E

除非有明确理由，不跳阶段。

## 什么时候应该停下来先讨论

以下情况先暂停编码并重新对齐：

- 需求边界突然变大
- 需要删除或覆盖既有行为
- 发现当前分支还没合并，不能安全收口
- 遇到和当前任务直接冲突的未预期改动
- 需要在“快速修补”和“结构性改造”之间做取舍
- 对话已经很长，怀疑当前执行目标和最近总结内容串线

## 上下文重锚清单

当出现长对话、多轮中断、连续收口、多个窗口并行改同一仓库时，先按下面清单重锚：

1. `git status --short --branch`
2. `git branch --show-current`
3. 当前工作区是否有未提交改动
4. 当前目标一句话复述
5. 当前不做什么一句话复述
6. 当前下一步动作一句话复述

只有这 6 项确认完，才继续编码或收口。

## 简版清单

每次开发前后都可以用这张清单快速自检：

### 开始前

- 已对齐目标
- 已写计划
- 已从 `main` 拉分支

### 提交前

- 代码改完
- README 已同步
- 中文注释已补
- 测试 / lint / build 已跑

### 合并后

- 已切回 `main`
- 已拉最新
- 已删本地分支
- 已删远端分支
